§1项目背景

目标场景：2026-05-09 12:45–18:00（Europe/Amsterdam），200–300 名荷兰华人数据从业者线下 meetup。

核心价值：让参会者把"求助 / 组队 / 内推 / 观点 / Q&A"广播给全场 200 人，而不是只能跟身边 5 个人聊。配合 AI 撮合，主动推荐"应该跟谁聊"。

边界：单场即弃，无多租户、无 DM、无邮件基础设施。活动结束 7 天内可通过恢复链接登录看回顾。

计划上线：自定义域名 meet.zhaidewei.com，部署在 Cloudflare Workers + Supabase（数据 + Realtime）。

§2当前业务流

普通参会者
扫 QR 进入→ 输活动密码→ 浏览 timeline→ 发帖（含 tags + 联系方式开关 + 私下 AI 撮合）→ 收到点赞 / 回复 / AI 推荐→ /me 看自己状态

浏览器 UUID 即身份，无登录摩擦。换设备可走 /me 复制恢复链接 7 天内还原身份。

嘉宾（VIP）
vip-login（用户名+密码）→ 实名 + 职位自动展示→ 普通发帖能力+ 发起投票（单/多选 + 隐藏结果选项）

~10 名嘉宾，主办方预录入用户名+密码。1 个嘉宾 token ↔ 1 个 user 行，跨设备登录共享同一身份。

现场主屏 / 投影
/screen 路由→ 焦点帖子轮播（1 大 + 4 小）→ 活动投票全屏接管→ 右下 QR + 在线人数

4 时钟 state machine：UI 1s / 焦点 8s / 投票槽 30s / 服务端轮询 10s。Realtime 接入后可去掉轮询。

§4架构概览

graph LR Browser["浏览器
(uid + pw cookie)"] -->|HTTPS| Next["Next.js Server
(Server Actions)"] Next -->|service_role key| Supa[("Supabase Postgres")] Browser -.->|anon key 只读 Realtime| Supa Cron[("pg_cron")] --> Edge["Edge Function
DeepSeek 撮合"] Edge --> Supa

关键决策

  • 无 Auth：浏览器 UUID + cookie 即身份。降低参与摩擦，代价是身份依赖 cookie
  • 服务端写 + 公开 RLS 读：所有写经 Server Actions（service_role），客户端只用 anon key 做 Realtime 订阅
  • 恢复链接：每个 user 行有 recovery_token，URL 形式可跨设备 7 天内换回身份
  • VIP 跨设备一致：1 vip_token ↔ 1 user 行，登录时复用
  • 撮合方案 F''：发帖时附暗字段，AI 以 reply 形式内联回复，不增加新 tab

技术栈

  • Next.js 16.2.4（App Router · Server Components · Server Actions · Turbopack）
  • Supabase（Postgres + Realtime + Edge Functions + pg_cron）
  • Cloudflare Workers（部署目标，via @opennextjs/cloudflare）
  • TypeScript · Tailwind v4 · Vitest
  • DeepSeek（撮合 LLM）

§7设计澄清 · AI 撮合不走 RAG（5/3 补充）

队友提问："AI 撮合是不是用 RAG 拿所有数据？"
答：不是 RAG，是"胖 prompt"——把候选池一次性塞进上下文让 LLM 自己挑。

当前设计的数据流（slice 3 待实现，但形态已定）

[每 5 min pg_cron 触发 Edge Function]
  ↓
1. 取所有有 match_intent 且未生成 AI reply 的 posts
2. 取所有"候选用户" — 有 nickname/company 或最近发过帖的 users
3. 拼一个 prompt：
   ┌─────────────────────────────────────────┐
   │ A 想找 [match_intent 文本]              │
   │ A 在公开 feed 里发的帖子: [body 摘要]    │
   │                                          │
   │ 候选人列表（200 人）：                   │
   │   B  · 公司X · 最近发过：[posts]        │
   │   C  · 公司Y · 最近发过：[posts]        │
   │   ... ×200                              │
   │                                          │
   │ 请选最合适的 1-3 人推荐给 A...          │
   └─────────────────────────────────────────┘
  ↓
4. DeepSeek 整段读完，返回 JSON：[{user_id, reason}]
5. INSERT INTO replies (is_ai=true, mentioned_user_id, body=reason)

为什么不上 RAG（按 Occam 算的）

维度胖 promptRAG
用户规模200 人 / 单场1 万+
候选池 token~20-30K（DeepSeek 64K 绰绰有余）必须 chunk + retrieve
基础设施0（直接 SQL + LLM 调用）pgvector + embedding 模型 + 索引维护
召回质量LLM 看全量做组合优化top-K 召回会漏冷门匹配
实现成本slice 3 估 2-3 天+2-3 天

但是有个真问题：所有数据都流向 DeepSeek

这才是当前设计的隐忧（不是 RAG vs 胖 prompt 的事）：

流向 DeepSeek 的内容是否敏感
match_intent（私下暗需求）敏感 用户期望"仅 AI 看到"
发帖人公开 body已公开，无所谓
候选人 nickname / company用户同意公开才填的
候选人 contact_handle不应流出 只在帖子作者主动 reveal 时显示，LLM 不需要

影响 Issue #1 P1.6 隐私公告决策：DeepSeek 是境外服务，把华人用户的私下意图 + 真实姓名 + 公司发过去，需不需要在活动前明确告知？
